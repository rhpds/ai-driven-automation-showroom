= Section 1.1 - Instana Observability and Infrastructure Monitoring
:navtitle: Instana Observability and Infrastructure Monitoring

*Estimated time: 15-20 minutes*

== Objective

In this section, we will explore **IBM Instana**, an enterprise-grade observability platform that provides real-time monitoring, intelligent alerting, and automated incident detection. This section demonstrates how observability platforms integrate with Ansible Automation Platform for intelligent remediation workflows.

Instana continuously monitors your infrastructure and applications, detecting anomalies automatically. When issues occur, it generates alerts that trigger automated remediation through Event-Driven Ansible, creating a complete closed-loop AIOps workflow.

== Learning Objectives

After completing this module, you will be able to:

* Navigate the Instana observability platform and understand its core components
* Locate your own monitored host in the infrastructure map using your zone
* Understand distributed tracing and service metrics through the Services tab
* Read an Instana Smart Alert webhook payload and understand which fields drive automation
* Describe the two remediation paths used in this lab and when each applies

== What is Instana?

Instana is an observability and application performance monitoring (APM) platform that provides:

* **Full-stack observability**: Monitor infrastructure, containers, applications, and synthetic transactions
* **Automated discovery**: Automatically detects and monitors services, dependencies, and infrastructure
* **Smart Alerts**: Detects anomalies in service behavior and raises incidents
* **Action Catalog**: Imports Ansible Automation Platform job templates and recommends them against live incidents
* **Closed-loop remediation**: Triggers automated responses through webhooks and API calls

In this lab, Instana monitors a **Flask web application** running on `node2`. The Instana agent collects metrics about service latency, error rates, throughput (calls), and infrastructure health. When the application stops responding and calls drop to zero, Instana detects the anomaly and sends a webhook to Event-Driven Ansible, which triggers remediation in Ansible Automation Platform.

== Understanding Instana Components

The infrastructure map shows all monitored hosts, grouped into **zones**. In this workshop, zones are the **student separation layer**: every student environment reports into its own zone, named after that student's `{guid}`. Your lab's RHEL node2 — the host running the Flask web application — shows up in the map attached to your `{guid}` as its zone, together with the Instana agent and every process it discovers on that host.

**Your zone name is**: `{guid}`

. Locate the tower labelled `{guid}` in the map — this is your host, and everything inside it belongs to your lab environment

The Python Instana SDK is loaded by the Flask application, so these traces are produced by real instrumentation rather than synthetic checks.

=== 3. Smart Alerts

Smart Alerts monitor a service and raise an incident when its behaviour changes. In this lab we use a Smart Alert on the **Throughput** (calls) metric:

* **Metric**: calls (throughput)
* **Condition**: operator `<`, **Critical** enabled with numeric value `1`, and **Warning** disabled; the condition is calls below one per minute
* **Time threshold**: a 1-minute evaluation window and one consecutive violation (1 minute of persistence)
* **Grace period**: 1 minute after persistence is set, so the incident closes shortly after traffic resumes
* **Scope**: **Per service for this application perspective**, with the Application Perspective containing only `lab-webapp-{guid}`
* **Channel**: a generic webhook pointing at your Event-Driven Ansible listener

[NOTE]
====
Smart Alerts cannot be attached straight to a service. They are always created in the context of an **Application Perspective**, a scoped view of one or more services. In the next module you will therefore build the alert in two stages: first an Application Perspective wrapping your service, then the Smart Alert inside it.
====

The alert has two states that matter to automation:

* **OPEN**: the service is down and remediation should run
* **CLOSED**: the service has recovered and the incident is resolved

[NOTE]
====
Instana Smart Alerts can use machine learning baselines, but in this lab we set an explicit `< 1` threshold. It is deterministic, which makes the exercise reproducible inside a short workshop slot.
====

== The Instana Webhook Payload

When the Smart Alert fires, Instana sends an HTTP POST to the configured channel. The following payload was captured from a real alert in this lab environment:

[source, yaml]
----
issue:
  state: OPEN                                 # OPEN when raised, CLOSED when resolved
  type: incident
  severity: 10
  entity: Service
  entityLabel: lab-webapp-ds2nq               # service name, ends with the student guid
  metricName: calls
  metric: "0.000"                             # current value: no calls at all
  thresholdValue: "1.0"
  calls: "0.000 < 1.000"
  text: Number of calls is anomalously low    # human readable alert text
  link: https://unit0-techzone.../events;eventId=...
  start: 1791404942004
  zone: not available                         # service-scoped alerts carry no zone
----

Three fields drive the automation:

[cols="1,3", options="header"]
|===
| Field
| Why it matters

| `issue.state`
| The rulebook only acts on `OPEN`. `CLOSED` is logged so you can see recovery.

| `issue.entityLabel`
| Carries your `{guid}` as a suffix. The rulebook strips `lab-webapp-` from it to work out which student's job template to launch.

| `issue.text`
| "Number of calls is anomalously low". This text is what the Action Catalog matches job templates against in Path 2.
|===

One more field worth knowing: `issue.severity` is `10` for Critical alerts like the one you will create, and `5` for Warning. The rulebook in this lab does not use it, but it is useful for filtering events in the activation history.

[IMPORTANT]
====
The payload sent by the **Test channel** button in the Instana channel configuration is a `change` event and contains **no** `state` field. The rulebook condition is `event.payload.issue.state == "OPEN"`, so a test alert will reach Event-Driven Ansible but will not launch a job. Only a real firing alert triggers remediation.
====

== Two Paths to Remediation

This lab deliberately wires up two different ways to get from an Instana incident to an Ansible job. Both run the same job template in the end.

=== Path 1: Automated remediation through Event-Driven Ansible

Instana posts the alert to a webhook. The **Instana AIOps** rulebook activation running in Ansible Automation Platform matches the event and launches the restore job with no human involved:

[source, yaml]
----
- name: "Trigger AI remediation on Instana OPEN alert"
  condition: event.payload.issue.state == "OPEN"
  actions:
    - run_job_template:
        name: "INSTANA | {{ event.payload.issue.entityLabel | replace('lab-webapp-', '') }} | Restore Web App Service - Fix anomalously low calls"
        organization: "Instana AIOps"
        job_args:
          limit: "node2"
          extra_vars:
            instana_entity_label: "{{ event.payload.issue.entityLabel }}"
            instana_alert_text: "{{ event.payload.issue.text }}"
            instana_metric: "{{ event.payload.issue.metric }}"
            instana_alert_state: "{{ event.payload.issue.state }}"
----

Note how the template name is built at runtime from `entityLabel`. With your service named `lab-webapp-{guid}`, the shared rulebook routes its alert to the restore template containing your `{guid}`. This naming convention is not an access-control check; keep your service and alert scoped to your own GUID.

**Strengths**: fastest possible response, no human in the loop, predictable for well-understood failures.

=== Path 2: Operator-driven remediation through the Action Catalog

Instana polls Ansible Automation Platform and imports the job templates it is allowed to see into its **Action Catalog**. When an incident is open, Instana matches the incident text against the names and descriptions of those actions and surfaces the most relevant ones as recommendations. An operator picks one and runs it from the Instana UI.

**Strengths**: a human chooses between several candidate remediations, every run is attributable, and the decision is recorded.

[NOTE]
====
In this workshop you will run the action from the Instana UI yourself — Section 1.2 walks you through it, including two cautions that matter in a shared instance: run only actions carrying your own `{guid}`, and commit the host limit properly before running. If you would rather not run anything, Section 1.2 also shows how to restore from Ansible Automation Platform instead.
====

=== Comparing the paths

[cols="1,2,2", options="header"]
|===
| Aspect
| Path 1 (Event-Driven Ansible)
| Path 2 (Action Catalog)

| Trigger
| Webhook from the Smart Alert
| Operator clicks in the Instana UI

| Human involvement
| None
| Required

| Response time
| Seconds after the alert fires
| As fast as someone responds

| Best for
| Known, safe, repeatable fixes
| Ambiguous incidents, changes needing approval
|===

[NOTE]
====
These are complementary, not competing. A mature AIOps practice automates the failure modes it trusts and routes the rest to an operator with good recommendations attached.
====
