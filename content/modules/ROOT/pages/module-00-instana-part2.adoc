= Section 1.2 - Smart Alerts and Dual-Path Remediation
:navtitle: Smart Alerts and Dual-Path Remediation

*Estimated time: 30-40 minutes*

== Objective

In this section you will connect Instana to Ansible Automation Platform and exercise both remediation paths. You will create a webhook alert channel, an Application Perspective, and a Smart Alert, then break the Flask application and watch Event-Driven Ansible restore it automatically. Finally you will break it again with automation disarmed, and see which remediation Instana recommends for the incident and why.

By the end of this module you will have a working closed loop: Instana detects the outage, automation repairs it, and Instana confirms the recovery.

== Learning Objectives

After completing this module, you will be able to:

* Identify the Ansible job templates provisioned for your environment and verify their target host
* Create a generic webhook alert channel that targets your Event-Driven Ansible listener
* Create an Application Perspective and a service-level Smart Alert scoped to it
* Trigger and observe fully automated remediation through Event-Driven Ansible
* Read the NLP-ranked remediation recommendations Instana surfaces on a live incident
* Explain when each path is the right choice

== Step 2: Confirm the Event-Driven Ansible Listener Is Running

Path 1 depends on a rulebook activation that is already running for you.

. Confirm that **Instana AIOps** shows status **Running**

image::instana_eda_activation_running.png[Instana AIOps rulebook activation running, link="_images/instana_eda_activation_running.png", window=blank]

[NOTE]
====
**What is a Rulebook Activation?** A rulebook activation is a long-running listener managed by Event-Driven Ansible. It watches for incoming events — in this case, webhook payloads from Instana — and evaluates them against a set of rules. When an event matches a rule's conditions, the activation automatically triggers the corresponding action, such as launching a Job Template. Think of it as an always-on "if this, then that" for your automation platform.
====

This activation runs the `instana.yml` rulebook, which listens for webhooks on port 5000. An `OPEN` issue launches remediation; a `CLOSED` issue records recovery without launching another job.

Your webhook URL is:

[source, text, subs="attributes+"]
----
{eda_webhook_url}
----

[NOTE]
====
The listener runs inside Ansible Automation Platform as a rulebook activation, not as a service you manage on the bastion. Use **Automation Decisions** -> **Rule Audit** to inspect events that matched a rule and the resulting actions. The activation's **History** tab shows activation runs and their output.

== Step 4: Create the Application Perspective and Smart Alert

Instana does not let you attach a Smart Alert directly to a service. Smart Alerts are created in the context of an **Application Perspective**, so this is a two stage process:

. Create an Application Perspective containing your service
. Create a Smart Alert inside that Application Perspective

== Comparing the Two Paths

You saw the same remediation reached two different ways: once triggered by a rule, once selected by a person.

[cols="1,2,2", options="header"]
|===
| Aspect
| Path 1: Event-Driven Ansible
| Path 2: Action Catalog

| Trigger
| Webhook from the Smart Alert
| Operator selects an action in Instana

| Decision made by
| A rule written in advance
| A person, at incident time

| Time to remediation
| About two minutes, unattended
| As fast as someone responds

| Attribution
| The rulebook activation
| The operator who ran the action

| Choice of remediation
| Fixed by the rule
| Chosen from ranked recommendations

| Best suited to
| Known failure modes with a safe, single fix
| Ambiguous incidents, or changes requiring judgement

| In this workshop
| Fully functional
| Fully functional — run it from Instana (watch the host limit) or from AAP
|===

Use Path 1 where the failure mode is understood and the fix is safe to apply unattended. Use Path 2 where the correct response depends on context a rule cannot capture, or where your change process requires a person to decide.

Most organisations run both. The value of the Action Catalog is that the operator making the judgement call is handed a short, ranked list of validated automation instead of a blank terminal.

== Taking It Further: AI-Driven Remediation

In Path 1, Event-Driven Ansible remediated the incident directly: the rulebook matched the alert and launched one job template, pre-selected by you when you wrote the rule. The decision was made in advance.

The next step is to let the automation itself choose the remediation. Your job templates are already in Ansible Automation Platform and your actions are already in the Instana catalog — so you can bake AI into the playbooks and build an **AI router and dispatch pattern**:

- an **AI router** job receives the Smart Alert payload and asks a large language model to pick the most likely remediation from your **complete automation catalog**, not from one hardcoded mapping — the payload already carries the incident text, the affected entity in `entityLabel`, and Instana's own remediation hint in `issue.suggestion`
- an **approval gate** pauses the workflow so a human reviews the AI's choice before anything executes
- a **dispatcher** launches the approved job template against the affected host

=== The pattern in playbooks

The pattern is three nodes in an Ansible Automation Platform workflow:

[grid=cols]
|===
|Node 1 |Node 2 |Node 3
|`ai_route_remediation.yml` — AI picks the template |Workflow *approval node* — you review and approve |`dispatch_remediation.yml` — launches the approved template
|===

The workflow, as it appears in the AAP Workflow Visualizer — the AI router feeding the approval gate:

image::instana_workflow_router_approval.png[Workflow Visualizer: ai_router to approval, link="_images/instana_workflow_router_approval.png", window=blank]

and the approval gate feeding the dispatcher:

image::instana_workflow_approval_dispatch.png[Workflow Visualizer: approval to dispatch, link="_images/instana_workflow_approval_dispatch.png", window=blank]

The snippets below are from a working demo of this pattern against Instana alerts. The AI router fetches your job template catalog from the AAP API and asks the LLM to pick one:

[source,yaml]
----
- name: Fetch job template catalog from AAP
  ansible.builtin.uri:
    url: "https://{{ controller_host }}/api/controller/v2/job_templates/?page_size=100"
    method: GET
    headers:
      Authorization: "Bearer {{ controller_token }}"
    status_code: 200
  register: jt_response

- name: Build LLM prompt
  ansible.builtin.set_fact:
    llm_prompt: |
      You are an AIOps routing agent. An observability alert has fired and you must
      select the single best remediation action from the job template catalog below.

      ALERT CONTEXT:
      - Text: {{ alert_text }}
      - Severity: {{ alert_severity }}
      - Entity Label: {{ alert_entity_label }}
      {% if alert_suggestion | length > 0 %}
      - Instana Suggestion: {{ alert_suggestion }}
      {% endif %}

      JOB TEMPLATE CATALOG (from Ansible Automation Platform):
      {{ template_catalog }}

      INSTRUCTIONS:
      - Select exactly ONE job template that best remediates this alert
      - If confidence is below 70% or nothing clearly matches, set template to "ESCALATE"
      - Respond with ONLY a JSON object:
      {"template": "<exact template name>", "confidence": <0-100>, "reasoning": "<one sentence>"}
----

The alert context comes straight from the Instana webhook payload you examined in Part 1 — `alert_entity_label` is the payload's `entityLabel`, and `alert_suggestion` is `issue.suggestion`. Anything Instana already tells you about the incident is free routing signal.

The router then records its decision and hands control to the workflow:

[source,yaml]
----
- name: Pass routing decision to workflow via set_stats
  ansible.builtin.set_stats:
    data:
      selected_template: "{{ routing_decision.template }}"
      routing_confidence: "{{ routing_decision.confidence }}"
      routing_reasoning: "{{ routing_decision.reasoning }}"
      alert_fqdn: "{{ alert_fqdn }}"
      alert_entity_label: "{{ alert_entity_label }}"

- name: Fail the node if AI says ESCALATE
  ansible.builtin.fail:
    msg: >-
      AI router selected ESCALATE (confidence: {{ routing_decision.confidence }}%).
      Alert '{{ alert_text }}' does not match any known remediation.
      Sending to on-call team for manual investigation.
  when: routing_decision.template == "ESCALATE"
----

`set_stats` is how the three nodes share state: the approval node pauses the workflow for a human decision, and the dispatcher reads the same stats. Failing the node on `ESCALATE` routes low-confidence incidents to a person instead of guessing.

Finally, the dispatcher launches the approved template against the affected host:

[source,yaml]
----
- name: Find job template by name in AAP
  ansible.builtin.uri:
    url: "https://{{ controller_host }}/api/controller/v2/job_templates/?name={{ selected_template | urlencode }}"
    method: GET
    headers:
      Authorization: "Bearer {{ controller_token }}"
    status_code: 200
  register: template_lookup

- name: Launch remediation job template
  ansible.builtin.uri:
    url: "https://{{ controller_host }}/api/controller/v2/job_templates/{{ template_lookup.json.results[0].id }}/launch/"
    method: POST
    headers:
      Authorization: "Bearer {{ controller_token }}"
    body_format: json
    body:
      extra_vars:
        target_host: "{{ alert_fqdn }}"
        entity_label: "{{ alert_entity_label }}"
        routed_by: "ai"
        routing_confidence: "{{ routing_confidence }}"
    status_code: [200, 201]
  register: launched_job
----

Notice the dispatcher never contains remediation logic itself — it looks up whatever template the AI selected and launches it. That is what makes the pattern catalog-driven: add a new remediation job template to AAP and the router can pick it immediately, with no playbook changes.

The dividing line to keep in mind: **rules for known failure modes, AI for everything else**. Path 1 is faster and fully predictable, but only covers what you wrote a rule for. The AI-routed pattern trades a little latency for coverage of incidents nobody anticipated — and the approval gate is what keeps it governed: every AI decision is reviewed, attributable, and auditable before it touches a host.
